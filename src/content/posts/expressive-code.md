我現在比較少看到一個專案就直接開始改。

尤其是接手別人的程式碼時。

第一步通常是先看。

看目錄、設定檔、資料結構、部署方式，再找真正負責某個功能的檔案。

因為很多時候，問題根本不是「缺少一段程式」。

而是原本已經有一套東西，只是自己還不知道它在哪裡。

## 小修改比較舒服

找到位置之後，我會盡量一次只處理一件事。

例如先改網站名稱。

確認沒問題，再改個人資料。

再確認一次，接著才處理下一個頁面。

這樣如果出問題，比較容易知道是哪一步造成的。

Git 的 commit 也會因此比較有意義。

看到歷史紀錄時，不會只剩下一個巨大到不知道改了什麼的 commit。

## 最後才是大整理

等整個結構真的摸熟了，再決定哪些地方值得重構。

有些看起來醜的程式碼，其實正在負責某個不能隨便破壞的功能。

所以我現在比較相信：

**先理解，再修改。**

速度可能慢一點，但比較不容易把一個本來能跑的東西改到完全不能跑。
